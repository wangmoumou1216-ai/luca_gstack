## 3. 为什么在位方案赢（这轮真正的判据）

| 维度 | mermaid（在位） | archify（候选） |
|---|---|---|
| 安装 | 0（渲染器随环境/查看器） | 需下载 1.8MB + Node |
| 产物形态 | **仓库内文本块**，可 grep、可 diff、可版本化 | 外部 800KB HTML，**你的 grep 原则够不着它的内容** |
| 治理成本 | 0 | 三行台账 + 配额 + 退役计数器 |
| 契合你的原则 | ✅ 决策靠可被 grep 的东西 | ✗ 与之为敌 |
| 可迭代 | ✅ 改文本 | ✅ 改 JSON |

**决定性论据**：反方一直主张「你的决策依赖可被 grep 的契约文字，不依赖图」——这条打 archify 是对的。而 mermaid 恰好是**把图变成可被 grep 的文本**。所以在这套体系里，mermaid 是 archify 的上位替代，不是下位。

## 4. 终局

### 默认：**不采纳**（自动生效）

### archify 真正独占、mermaid 做不到的只有两件事

| 场景 | mermaid 能吗 | 处置 |
|---|---|---|
| **merge 前架构变更评审**（Before / Delta / After 三态对比） | ❌ 做不到 | 需要时走按需探针 |
| **对外高保真交付图**（交互探索、PNG/WebM 导出、品牌化） | ❌ 做不到 | 需要时走按需探针 |

除这两个场景外，一律用 mermaid。

### 能力保留：零安装按需探针（20 秒，用完即删）

```bash
curl -sL "https://raw.githubusercontent.com/tt-a1i/archify/main/archify.zip" -o /tmp/archify.zip
unzip -q -o /tmp/archify.zip -d /tmp/archify_probe
cd /tmp/archify_probe/archify && ARCHIFY_UPDATE_CHECK_DISABLED=1 node bin/archify.mjs doctor
```

### 想强化图表能力时的**优先路径**

**不是引入 archify，而是强化现有 mermaid 管线**：
- 给 mermaid 补渲染/校验环节（最接近 archify 的"可验证"收益，成本最低）
- 把 PRD 模板里那个 mermaid 块扩成一套图规范（流程/时序/状态/数据流的标准写法）
- 三处 harness 目录的模板重复，先收敛成单一真值源

## 6. 今天真正该进 governance 的教训

1. **被截断的否定结果不是证据**——本案第二次栽在同一类错误上（第一次把图标库当图，第二次把 timeout 掐出的 0 当真值）。**凡"零命中"结论，必须报出扫描文件数与方法，否则无效。**
2. **先看在位方案再评候选**：前三轮都在真空里评 archify，没人看一眼仓库里 mermaid 已经制度化。正确顺序是「在位方案 → 差距 → 候选」，本案差距根本不在这。
3. **杀提案 ≠ 驳论据**（v3 已记）
4. **提倡者不得自判**（v3 已记）
