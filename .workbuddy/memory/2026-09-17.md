- 起因：lucas 质疑"真握手了？没有反对方？" → 重开一轮：独立反对 party + 程序审计。审计给原 loop 判 C（严格 D）：第 3 轮起"要采纳"成预设，仲裁者驳的是提案而非论据（杀提案代驳论点）。
- **自我更正**：此前反复引用的"你已有 80 个手绘 SVG"是错的——那是 framework/assets/figma-icons/ 的 UI 图标资源（30 被引/50 备用），全工作区 framework 之外 `*.svg` 数量 = 0。该论据撤回。
- 关键判据（三重零，落到实证）：全库 md 中"如下图所示/见下图"= 0 处；"流程图/架构图"= 0 处；现存图表类资产 = 0 个 → **倾向「无需求论」而非「缺口论」**：这套 OS 不生产也不消费系统图，决策靠可 grep 的契约文字，交接靠 references + memory 三层。

### archify 终局 v4.0（定稿，取代 v3）

- **撤回两条错误依据**：①「你已有 80 张手绘 SVG」实为 framework/assets/figma-icons/ 的 UI 图标库；②v3 的「三重零无需求论」是假阴性——`timeout 90` 掐断 grep 后被我误读为 0。Python 全量重扫 11,241 份 md 的真实命中：流程图 279、mermaid 65、architecture diagram 33、时序图 18、架构图 13，含真实 mermaid 代码块的文件 34 份（语料有效：抽样 200 份中 143 份含中文）。
- **决定性发现**：sharedev项目 的 PRD 模板（.claude/specs/、.codex/specs/、.sharedev/specs/ 三处各一份）已内置 mermaid 流程图块（graph TD 触发条件→条件判断→操作→更新数据→完成）→ **图能力已制度化，载体是 mermaid**。
- 终局：**默认不采纳 archify**。理由不是"没需求"，而是"在位方案更契合"——mermaid 零安装、仓库内文本块、可 grep/可 diff/可版本化，正合"决策靠可被 grep 的东西"原则；archify 产物是外部 800KB HTML，与该原则相悖。
- archify 仅两个独占窄场景保留（按需探针 /tmp 拉起 20 秒）：merge 前架构变更 Before/Delta/After 三态对比；对外高保真交付图（交互 + PNG/WebM 导出）。
- 想强化图表能力的优先路径 = 强化现有 mermaid 管线（补校验 / 扩 PRD 模板图规范 / 收敛三处 harness 模板重复），不是引入外部件。
- 文件：.workbuddy/archify-采纳终局-v4-2026-09-17.md（现行真值）；v1/v2/v3 均已标注废止留痕。
- 教训（最重要一条）：**被截断的否定结果不是证据**——凡"零命中"结论必须报出扫描文件数与方法，否则无效。本案两次栽在同一类错误上。
