## 一、被审体系速览

真值源 `model-routing.yaml`（v2, 2026-07-10）定义 4 档：`reasoning-heavy→fable`、`core-execution→opus`、`guided-execution→sonnet`、`mechanical→haiku`；`fable_whitelist`（P0/P1/P2）授权 fable 使用点；`codex:` 段（2026-08-04）为 Codex 侧唯一解析表：`tier_to_effort` 四档→`xhigh/high/medium/low`，`model_reasoning_effort` 落档、绝不写死模型名。

投影点：CLAUDE.md 速查表（S33 守护）→ orchestrator.md → 40 个 SKILL.md frontmatter（每日治理守护）→ `.codex/agents/*.toml`（S8b 守护）→ `.codex/workflow-runner.mjs`（自称引用 yaml 实为复制，仅 S8c 查禁用值）→ AGENTS.md §4.8.2/§11。

**核心设计优点（先说结论里好的部分）**：按能力档而非模型版本定义路由、fable 白名单 + 手术刀式收敛（配额降 80-95%）、档位不变量 = 相对序、Codex 侧拒绝写死模型名（2026-08-04 订阅失效实证）、S8c 把实测禁用值硬编码在检查脚本侧防 yaml 松动、枚举以真实模型接受集为准（minimal 教训）。这套设计思想是自洽且先进的。

## 二、最终发现清单（经 3 轮对抗收敛）

### MAJOR（4 项，机制性缺口）

**F1 · fable dispatch 零机械执法、零审计痕迹**
- 证据：`fable_whitelist` 为自然语言条目（yaml:73-84）；`daily_governance.check_model_routing`（L130-234）不解析该段；observability/ 目录 grep "fable" 零命中；`.claude/settings.json` PreToolUse matcher 不含 Task/Agent。
- 影响：按本仓自设标准（verify-codex-wiring.mjs:161「自证式门禁不是门禁」），纯 prose 纪律不算门禁。P2 翻案复审时用户无法验证上次 dispatch 是否越权。
- 对抗轨迹：R1 曾降 MINOR（prose 合同存在），R2 恢复 MAJOR——本仓先例明确 prose-only 不算门禁。
- 修复方向（R3 裁决）：正解是加 PreToolUse(Task|Agent) hook 机械读取 `tool_input.model` 校验 ∈ 合法别名集并落盘审计 jsonl（执法为主、审计为副产品）——靠 AI 自觉写审计 = 自证问题复活。

**F2 · workflow-runner 双写无对账（+触发路径盲区）**
- 证据：`.codex/workflow-runner.mjs:74-76` `TIER_TO_EFFORT`/`PHASE_TIER` 硬编码，自称「真值源是 yaml 的 codex.tier_to_effort」实为复制；S8c 只查拒绝集（minimal）、不查映射相等性；PHASE_TIER 未登记 phase（Load/Intake/Discover）静默落 medium；治理触发三路径（launchd 每日、fusion-preflight skill 变更、S33 速查表）无一校验 codex 段↔runner 相等性。
- 影响：改 yaml codex 段后 runner 静默漂移；若 Redteam phase 映射被改坏，框架演进红队审查静默降档。
- 对抗轨迹：R1 以「漂移面仅 2 个月度 workflow」降 MAJOR；R2 维持 MAJOR 并与 D8 合并（触发盲区同根因）。
- 修复方向（R3 裁决）：verify-codex-wiring.mjs 加 S8d 断言，但用**单向包含**（yaml codex.tier_to_effort ⊆ runner TIER_TO_EFFORT + PHASE_TIER 值域 ⊆ tier 名集合）——逐值相等会误伤 runner 未来加降级链（runner 当前无 fallback，模型不可用直接 done(null)，与 yaml Claude 侧 fallback: opus 不对称）。

**F3 · Codex 侧 P0 升档规则缺失（判官双重降档）**
- 证据：yaml:88 Claude 侧 quality-gate「由调用方参数升 fable（P0）」；codex 段（yaml:154）与 quality-gate.toml 静态钉死 effort="high"，无 effort 覆盖通道；dispatch_rules 全部基于 Claude Agent tool 的 model 参数机制。
- 影响：code-hygiene（tier-2，codex-viability.yaml:48 明示 review 段在 Codex 派 quality-gate）调用路径真实存在 → Codex 上判官恒 high。违反 parity_note 自设规则「只补一侧 = 换个 CLI 就掉档」（yaml:157-159）。
- 对抗轨迹：R1 以「P0 场景假设性」降 MINOR；R2 恢复 MAJOR——调用路径非假设，掉档静默。
- 修复方向（R3 裁准）：yaml codex 段补「P0 场景 effort 升 xhigh」规则 + quality-gate 调用方合同写明 `-c model_reasoning_effort` 覆盖通道（仅注记力度不足）。

**F4 · 沙箱「仓库只读」宣称与 writable_roots 矛盾**
- 证据：AGENTS.md:375-379 与 runner:93/258 宣称「仓库写入被沙箱硬拦」；但 config.toml:45 writable_roots 首条即仓库本身（为 MEMORY_ROOT 记忆写入，缺它记忆路径全断——2026-08-06 实证）；config.toml:39 自己写着「仓库…无需列出」又在 L45 列出。
- 影响：安全宣称失真——agent 的工作根隔离到 tmp 但仓库在其可写白名单内，「硬拦」不成立。
- 对抗轨迹：R1 维持（config.toml:39 自供矛盾）；R3 澄清：**移除 writable_roots 仓库条目是错误修复**（会重造记忆写入断裂事故），正解是收窄为仓库内实际必写子路径 + 修正宣称文案。
- 修复方向：参照 config.toml:46 对 ~/.claude 的最窄口径，把仓库整条拆为 memory/、observability/ 等实际必写子路径（先枚举全部必写点，防造新断裂）；同步修正 AGENTS.md:375-379、runner 宣称。

### MINOR（4 项，措辞/覆盖级）

**F5** AGENTS.md:855（§11）枚举写 `none/minimal/low/medium/high/xhigh`——混入被实测拒绝的 minimal、漏 max，与 :403 及 yaml:142 接受集自相矛盾。AI 契约文件内的错误值会概率性误导 Codex AI；但按 L855 用 minimal 会 400 fail-loud 自暴露，非静默腐蚀。
**F5 修复**：按 harness 分册各定全集（模型侧拒绝 minimal；config 层合法），并补漏掉的 max。

**F6** yaml:128 principle 段仍用已否决的 minimal 作序关系示意底档（`xhigh>high>medium>minimal`），与 L142 取值表漂移。纯示意过时，无运行时影响。
**F7** daily_governance.py:193 无 frontmatter 的 agent 文件直接 continue——新增无-frontmatter agent 无存在性告警（现有 3 个无 frontmatter 文件恰好都在 agents_no_pin，当前无裸奔实例，是通道性缺口）。
**F8** 速查表守护（check-model-table + governance L220）只查 alias 子串——降级链文案「（不可用→降级 Opus）」可无痕剥离。属刻意宽松设计（防措辞锁死）的代价。

### 经对抗撤销/改写的项（诚实记录）

- **撤销**：「runner 默认档与 task_execution 矛盾」——yaml:115 workflow_tool 豁免覆盖 runner 行为，自决默认不违反真值源。
- **撤销**：「降级链无代码实现是缺陷」——yaml 规则 6 是给主循环 AI 的行为合同，prompt-driven 架构本意；Codex 侧订阅失效已有机器处理（runner:238）。
- **改写**：「≤7 天治理窗口」→ 实际三路触发（launchd 每日 9:07 定时，不依赖开 session），但三路无一覆盖 codex 段↔runner 对账（并入 F2）。
- **降级**：「S8c 硬编码禁用值会过期」→ R3 裁决这是防自证门禁的设计性钉子，与「过期快照」不同类；其时效风险由 review_after_days=90 覆盖，不构成发现。

### 流程元盲区（红队 R3 提出，经校准）

「意图→skill→tier→model」全链路中，skill-routing-map（意图→skill）与 model-routing（tier→model）两侧有守门，**中段 skill→tier 衔接（tiers.skills 数组）在提交路径上无即时守护**——新 skill 忘登任何 tier 时靠每日治理 digest 兜底（daily_governance L184 存在 tripwire，非零覆盖，但提交→治理运行之间有无信号窗口）。准确表述：**延迟守护，非裸奔**。另有主循环 /model 用户主权在白名单外属已知豁免，但缺审计面。

## 三、总评

| 维度 | 评级 | 说明 |
|---|---|---|
| 设计思想 | ★★★★★ | 能力档抽象、相对序不变量、白名单手术刀、拒绝写死模型名——自洽且先进 |
| Claude 侧守护 | ★★★★☆ | S33/S8b/S8c + 每日治理，提交路径即时 + 每日兜底，较完备 |
| Codex 侧守护 | ★★★☆☆ | runner 双写无对账（F2）、P0 升档缺失（F3）——「两个投影」纪律存在但机检只到 toml 层 |
| 执法与审计 | ★★☆☆☆ | fable 白名单纯 prose（F1），违反自设「自证式门禁不是门禁」标准 |

**一句话结论**：这是一套设计思想先进、Claude 侧守护扎实的模型路由系统；其系统性弱点集中在 Codex 侧投影的机检覆盖与 fable 白名单的执法面——4 项 MAJOR 全部是「文档纪律存在、机械对账缺失」型缺口，修复成本低（一个 hook + 一个断言 + 两条注记 + 一次收窄），但需按 R3 裁决的修法执行，避免两个已识别的错误修复方向（移除 writable_roots 仓库条目、逐值相等断言）。

**修复优先序**：F2（S8d 单向包含断言，成本最低）→ F1（PreToolUse Task hook 执法+审计）→ F3（codex 段 P0 升档规则）→ F4（writable_roots 收窄+文案修正）→ F5-F8（措辞统一）。
