## AI 工作台「通用组件 vs 按钮」分歧解答（2026-09-18 下午）

- 背景：luca 在 sharecrm 平台做 AI 工作台，标准通用组件进布局、调业务 skill 控制数据与洞察展示；开发认为按钮无法通用化。
- 我的结论（基于项目知识库 + 官方 PWC 文档证据）：**展示是"读"，按钮是"写"**。
  - 展示可通用：链路 skill → DTO → 组件渲染沙盒，执行者是组件自己，DTO 自描述、四态兜底，不依赖租户特定资源。
  - 按钮难通用：动作执行者是平台运行时（路由/对象写/BPM/权限/审计）；官方证据 `triggerMasterButton(buttonApiName)` 只能触发平台已注册按钮、按钮删除后动作失效；动作目标全是租户特定 apiName；平台缺少「动作协议层」（封闭动词集+绑定+校验）——类比组件世界的 function calling。
- 官方文档证据位置：`fktest10116/.sharedev/docs/pwc/docs/` 下 `reference/custom-plugin/web/objectform/context/bizApi/triggerMasterButton.md`、`toggleMasterButton.md`、`guide/scenes/app/layout-enhance.md`（布局组件定位"展示增强+局部交互"）、`guide/scenes/applink/`（跳转协议）。
- 过渡方案（已向 luca 提出）：受限动作描述符动词集（openAppLink/openDetail/callAPL/emitEvent）+ 租户级动作绑定配置；或"展示动态、按钮走平台 Button 资源静态配置"的组合。
- 追问（同日）：luca 指出平台本身有元数据、权限体系，为何不能直接支撑通用按钮。补充结论：现有元数据+权限服务于**静态配置模式**（管理员配置期固定按钮+权限绑定）；AI 工作台需要**动态声明模式**，缺两个标准合同——①语义解析合同（skill 意图 → 租户元数据资源映射）、②运行时权限合同（动作描述符+当前用户 → 可见/可执行），外加目标失效的兜底语义。元数据/权限/按钮运行时/AppLink 都是现成地基，缺的是协议层而非零件。
- 终问（同日）：「按钮不能通过 skill 做出来对吗？链路断在哪」。最终口径：按钮画得出、点得动，断的是**动作链**（5 段：意图✓→语义解析✗→权限判定✗→执行△只认注册 apiName→审计△只覆盖注册按钮）。缺的不是执行器，是动作世界的两个中间件：语义解析（翻译官）+ 运行时权限（安检员）。
- 补充条件（同日）：luca 表示**语义层和行业 knowhow 都有**。断点重新定位：断点一（意图→租户资源解析）由语义层自补，knowhow 决定"什么洞察配什么动作"。链路按读/写分岔：
  - **读动作（跳详情/跳页面/只读查询）：链路通**。语义解析 → AppLink/call_controller 现有通道执行 → 目标页自行权限拦截（懒校验，最坏=跳不动，可接受）。skill 驱动的通用读按钮**现在就能做，不等平台**。
  - **写动作（改数据/触发流程/提交审批）：仍断**。写必须前置拦截不能懒校验；权限真值只在平台，skill/语义层只能推断不能仲裁；执行通道只有"已注册按钮"一条且无动态审计。
  - 最终格局：剩余断点收敛为唯一一个——写动作的「前置权限真值 + 受控执行通道」，只能平台来架（语义层管"是什么"，权限体系管"可不可以"）。行动拆分：读按钮立即做；写按钮先走平台 Button 静态注册 + 动作协议立项推平台。
