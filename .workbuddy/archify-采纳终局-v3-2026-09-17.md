## 0. 一句话终局

**不采纳。零安装。能力以「按需临时探针」形态保留 —— 什么时候真出现需求，什么时候临时跑；一个季度内自然需求 ≥3 次才谈正式收养。**

## 1. 自我更正（先撤回我的错）

v1.0 与之前所有轮次里，反复用过一句论据：

> 「你 framework 目录里已有 80 个手绘 SVG，说明画图能力已被 LLM-SVG 满足，archify 边际价值有限。」

**这句话是错的。** 实测：

| 核查项 | 真实结果 |
|---|---|
| 那 80 个 SVG 是什么 | `framework/assets/figma-icons/*.svg` —— **UI 原型图标资源**，不是架构图|
| 被谁引用 | framework 的原型 HTML（list-page 引用 30 个，其余 50 个是备用图标库） |
| **framework 之外的全工作区`*.svg` 数量** | **0** —— 一张流程图/架构图/时序图都没有过 |

我把图标库读成了图作品，据此压低了 archify 的边际价值。**这条论据撤回。** 但更正之后往下继续查，得到的是**反方向的结论**。

## 2. 判据落地：缺口论 vs 无需求论

此前悬而未决的核心争点是：路由表零图表词条，既可读成「没工具→没需求」（缺口论），也可读成「没需求→没词条」（无需求论）。反对 party 给出的判据是：**看文档里有没有为「图需求」留下过痕迹**。实测三重零：

| 检验 | 结果 | 倾向 |
|---|---|---|
| 全工作区 md 中「如下图所示 / 见下图 / 下图所示」 | **0 处** | 无需求论 |
| 全工作区 md 中「流程图 / 架构图」字样 | **0 处** | 无需求论 |
| 存在的图表类资产 | **0 个** | 无需求论 |

**判读**：如果工具缺失压抑了真实需求，文档里应当留下「此处应有图」的斑痕（占位语、手绘图、或至少一次抱怨）。**一处都没有。** 这不是"缺工具"，是**这套治理操作系统真的不生产也不消费系统图**——决策靠可被 grep 的契约文字，交接靠 references 与 memory 三层。

## 3. 采纳许它在 v2.0 里成立的那根支柱，也塌了

v2.0（P5）最强的设计是「三行 primitives + 30 次零采纳自动退役」。独立反对 party 承认打不垮这根结构，但指出另外两处致命：

- **价值**：决策增量 ≈ 0，总价值小正（约 5–15%）——"更好看、可迭代"是审美增量，不驱动任何一次裁决或交接
- **取证**：三张真图由建议采纳方自出题、自执行、自判质量，**结构上不可能产出否定结论**（评级：仅能证明"能出图"，不能证明"该采纳"）。RT-2 当初要求的第三方盲评在后续轮次被静默丢失，至今未补。

程序审计另给整个 loop 判 **C（严格 D）**，理由是：第三轮起「要采纳」即成为预设，之后所有辩论只在争「怎么采纳最省」；仲裁者驳的是提案而非其论据（杀提案代驳论点）。

## 4. 终局方案

### 默认：**不采纳**（自动生效，不需要再议）

**代价为负**——把一个第三方外部件、三行台账、每会话一次建议配额、一个退役计数器全部从你的系统里移除干净。

### 保留能力的形态：零安装按需探针

```bash
# 需要一张图的时候（这条已经验证可用，约 20 秒）
curl -sL "https://raw.githubusercontent.com/tt-a1i/archify/main/archify.zip" -o /tmp/archify.zip
unzip -q -o /tmp/archify.zip -d /tmp/archify_probe
cd /tmp/archify_probe/archify
ARCHIFY_UPDATE_CHECK_DISABLED=1 node bin/archify.mjs doctor
```

已在 /tmp 验证过完整链路（doctor 17 项 ok / validate ok:true / deliver 产出 819,631 字节零外链）。用完 `rm -rf /tmp/archify_probe` 即可，**不占任何持久位置、不进 framework、不进路由、不需 pin**。

### 复启动议（唯一的回归通道，须同时满足）

| 条件 | 判据 |
|---|---|
| 自然需求锚定 | 一个季度内，**真实想图 ≥3 次**（不是"以后可能用得上"） |
| 且 | 当时**某个 md 里已出现真实占位需求**（例如写下"见 xxx.html"） |
| 且 | 说得出那张图**给谁看、支撑哪个具体决策**（不是"有了更好"） |

三条同时成立 → 按 v2.0 的三行 primitives 正式收养；不成立 → 议题**永久关闭**，不再进 review。

## 5. 终局判断为什么比 v2.0 硬

| 维度 | v2.0（三 primitives） | v3.0（不采纳 + 探针） |
|---|---|---|
| 治理税负 | 3 行台账 + 配额 + 退役计数器 | **0** |
| 休眠风险 | 有（"建议但不用"正是已退役的 advisory 反模式） | **0**（没有常驻，就没有休眠） |
| 供应链敞口 | 需 pin + watcher 才锁得住 | **0**（无持久安装） |
| 能力可得性 | 常驻 | 临时拉起，20 秒 |
| 默认动作 | 需到期裁决 | **自动生效，无需裁决** |

## 6. 本次 loop 的教训（进 governance 候选）

1. **杀提案 ≠ 驳论据**：本案最大程序缺陷。收敛前必须点名最强反方论据并说明它为什么错，而非只说明提案为什么输。
2. **提倡者不得自判**：任何"先试用再决定"的设计，若由提倡者出题、执行、判分，其证据力为零。必须独立取题 + 盲评。
3. **同一条证据的两种读法必须先致力于分辨**：本案「零词条」被双方反复借用，直到最后才用三重检验落地。
4. **给采纳一个零成本的备选形态**：本案真正的最优不是"最省的采纳"，而是"零安装按需探针"——把常驻形态换成按需形态后，「采不采纳」这道选择题本身被取消。
