# oracle 型 vs taste 型判据 — 什么能机械判定并自动修，什么必须交人

> **适用范围**：任何「发现问题后要决定自己修还是交人」的场景——评审后的修复、judge 判定、
> 自动化 gate、agent 自纠。原生于 `handoff-review` 的 auto-revise-once 机制（2026-06 由 luca
> review 并写入 `promoted-facts.yaml SC-20260615-002`），2026-08-03 提升为通用 reference。
> 被 `redteam` 判据挂载表引用。

## 1. 判定

| | **oracle 型** | **taste 型** |
|---|---|---|
| 本质 | 有客观真值，可机械核对 | 需要品味 / 权衡 / 领域判断 |
| 允许自动修复 | ✅ | ❌ **必须交人** |
| 判错的代价 | 低（错了能被同一把尺子测出来） | 高（错了会以「看起来合理」的形态留下） |

**缺省锁（最重要的一条）**：**判定有歧义时一律按 taste 处理**——保守优先，宁可交人。
自动修复的风险不对称：漏修一个 oracle 项只是少改一处，误自动修一个 taste 项会产出一个
「通过了检查但方向错了」的东西，而那正是最难被后续发现的缺陷。

## 2. 分类实例（来自真实评审项，可据此类推）

| 检查项 | 类型 | 为什么 |
|---|---|---|
| 品牌色一致 / 覆盖（`#FF8000` 出现次数、`--primary` 是否设置） | **oracle** | 可数 |
| 技术规范（Tailwind CDN/config、CSS 变量、间距是否合法值、JS 是否只做状态切换） | **oracle** | 对照白名单可判 |
| 状态完整性（空 / 加载 / 错误 / 成功态是否实现、空态是否非空白） | **oracle** | 存在性可判 |
| 契约完整性（prototype-spec / 交接块 的必填节是否存在） | **oracle** | 存在性可判 |
| 边界检查（PRD「不做什么」里的排除项是否出现了） | **oracle** | 对照清单可判 |
| 组件完整性 / 组件映射（清单项是否缺失） | **oracle** | 对照清单可判 |
| 优先级对齐（P0 是否比 P1 视觉更突出） | **taste** | 「更突出」无客观阈值 |
| 成功标准对齐（上线后能否达成指标） | **taste** | 依赖对业务的判断 |
| 需求覆盖 / P0 走通——**当失败描述含「需猜测」「绕道」这类判断语时** | **taste** | 判断语本身说明它不是机械核对的结果 |
| 信息架构 / 视觉重心一致性 | **taste** | 整体感知，无法拆成可数项 |

**整层封锁（比逐项判定更强的一条）**：**跨产物一致性层**（如 figma ↔ 原型、原型 ↔ 设计稿）**整层一律交人**，即使该层内某些失败项本身是 oracle 型（如 `--primary` 变量未覆盖、组件清单缺项）。
理由：修这类失败要重新生成上游产物，代价与波及面都远超单点修补。（此条源自 handoff-review 原设计的「节3 Figma 一致性整体一律交人」，2026-08-03 迁移时一度被降级为普通 taste 行，经实现后评审复原。）

**类推方法**：问一句「换一个不知道来龙去脉的人来核这一项，他会得出同样结论吗」——
会 → oracle；取决于他的品味或对业务的理解 → taste。

## 3. 有界自动修复的合法形态

即便全部是 oracle 型，自动修复也只在下列形态下成立（luca 2026-06 裁决，`SC-20260615-002`：
这是 luca_gstack「HARNESS 非 Loop」定位下的**唯一正向例外**）：

**进闸（三条全满足才进，缺一即交人）**
1. **首次失败**——同一审查链的第二次失败不再自动修。
   **计数责任在调用方**：实现本机制的角色必须自己维护「本链已自动修过几次」的状态（会话内变量或自己声明的字段均可）。**不要依赖 workflow-state 的顶层 `iteration`**——该字段的唯一写者已随 handoff-review 于 2026-08-03 移除，现在恒为初始值，读它会让本条闸恒真。
2. **失败项全是 oracle 型**——任一 taste 项即整体交人
3. **无 BLOCKED**——任一环节返回 BLOCKED 即交人

**上限**：`cap = 1`。修一次，重新全量复检，**绝不二次循环**。
（注意：修复后必须**重跑本轮全部检查项**，不能只复检修过的那条——上游重新生成的是整份新产物，
先前 PASS 的结论已失效。）

**fail-open 四触发**（任一命中即原样交人，不再尝试）
① 进闸未全满足 ② 修复或复检环节返回 BLOCKED / 异常 ③ 修复后仍未通过 ④ 任何不确定

**上下文隔离**：派给上游重新生成的 prompt **只含失败清单与目标文件路径，不附完整会话**——带上会话历史会让修复方沿着原判断走，失去独立性。

**不越权**：自动修复段本身不推进任何流程节点、不写状态，只把最终结果交给调用方。

## 4. 为什么这条判据值得单独存在

「能不能自动修」这个判断在每个自动化环节都会重新出现一次，而它**极易被乐观地答成"能"**——
因为自动修看起来更高效，且失败时的代价延后显现。把判据固定下来、把缺省锁定在「有歧义就交人」，
是让这个判断不随每次的乐观程度漂移。
