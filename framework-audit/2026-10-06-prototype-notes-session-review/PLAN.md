## 顺序

1. R1 / 审计：读取两会话全部用户指示与完成汇报；对照九个原 U-ID、冻结计划、实际源代码、交付文件、Git 与测试证据。输出 REVIEW.md，记录每项证据和缺口。门：无旧版证据冒充新版，无授权推导测试 PASS。
2. R2 / 独立代码审查：固定 review-input.json 的 111 文件 diff；Standards 与 Spec 分开冷审，包含可执行运行分区。门：真实 completed 与同次采用证据；Critical/Important 必须处理，未知保留。
3. R3 / 修复与验证：仅修实际 findings；首先校正 RELEASE 与最终 HTML 版本，增加有限可复跑的交付一致性检查，更新原本地 current-state 的当前指针并保留历史。复验真实浏览器状态显示、编辑下载重开、业务交互及内容不变。修后交原判官闭合。
4. R4 / 交付：在通过范围门后提交、推送、合并与主工作区快进拉回，核对相关 Git SHA 与受保护文件。原冻结计划 U008 的真实人类和原生宿主证据缺口单列；不声明整计划 DONE。

## 断言与质量准则

- BLOCKING R-A1：当前交付 HTML SHA 等于选定源汇报 SHA；extractNotes 成功，源 SHA、13 条说明、2 条人工、AI project-management scope、revision 6 与源元数据相同。
- BLOCKING R-A2：HTML 内嵌 runtime/style 与当前共享源一致；把指针改回 compact-02 必须被一致性检查拒绝，再还原 PASS。
- BLOCKING R-A3：Chromium/Firefox 对当前精确 HTML 打开面板、短状态、逐条编辑、下载重开与关闭后业务交互得到真实观察；合成输入不能冒充 OS IME/原生缩放。
- BLOCKING R-A4：review-input 冻结字节与评审对象一致；修后独立闭合，实际运行结果绑定相应版本。
- BLOCKING R-A5：提交仅含本任务文件；拉回后提交和交付 SHA 一致，原无关脏文件 hash 不变。
- C1：每项问题给出会话/文件证据，区分源会话问题与本会话接手错误。
- C2：全部原 U-ID 有状态依据；最新用户调整、Claude 排除、真实人类缺口没有遗漏或伪造关闭。
- C3：报告的验证结论限定实际运行范围，不把原测试分母或旧冷审升级为本次新版通过。

失败只停止依赖步骤，授权范围内最小修复；两轮独立复审仍有阻断则保留未决，不扩增审查层。各阶段当前状态见末尾检查点；历史计划顺序保留。
