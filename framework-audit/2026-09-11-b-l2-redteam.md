## 1. C1–C7 逐条裁决

### C1 · 不 fail-open — **NOT REFUTED**

机制核查（`project-substrate.mjs:816-855`）：`cursor` 是循环内局部变量，只在 `try` 成功分支于
`cursor = evidence.cursor_after` 处推进；`catch` 分支（跳过）从不触碰它。因此任何跳过都不会让后续候选
在"更靠前"的游标位置获得比对优势。`fail()` 只在 `event-attestation.mjs:516-517`（Codex）与 `:734-735`
（Claude）两处、且仅在"游标后第一条人类行"字节不匹配候选时才打 `next_native_turn_differs`；这两处都在
**找到匹配前直接 `return`**，不存在"先跳过再回头用同一 cursor 二次匹配出错误候选"的路径。

变异验证（见第 4 节 M1/M2）：把消费端判据从"必须带 marker"放宽到"只要是 MISMATCH 码就跳"，会让
"完整性类 MISMATCH 也被跳过"这条专门测试变红——证明当前耦合是真实生效的防线，不是装饰。

未能构造出任何队列/源记录组合，让 B-L2 在 dddf8e2 会拒绝的地方转而放行 TURN_ACTIVE/SWITCH_ONLY。

### C2 · 标记范围 — **NOT REFUTED**

### C3 · append-only 前提 — **NOT REFUTED（但发现一个真实的、未被此声称覆盖的场景，见 4.x/发现清单 F1）**

逐项攻击结果：
- **排队提示 queued/suggestion_accepted**：在 `CLAUDE_HUMAN_PROMPT_SOURCES` 白名单内，按普通人类行参与扫描，不构成乱序。
- **--resume 产生新 transcript**：`initializeProjectEventFence` 只在 SessionStart 且
  `source ∈ {startup, resume}` 时铸新 fence——append-only 只需要从"当次 fence/cursor 往后"成立，不需要
  跨越整个历史文件成立，resume 天然从新的边界重新起算，不构成违反。
- **rewind/编辑历史（parentUuid 分叉）**：`validateCursor` 对 `prefix_sha256` 做严格前缀哈希校验，游标之前
  的字节只要被改动（含 rewind 造成的历史重写）就会 `CURSOR_MISMATCH` 整体拒绝——这是既有基础设施（非
  B-L2 引入），fail-closed 方向正确。
- **Codex rollout 轮转**：`boundedCodexSource` 要求"仅一个匹配文件"，多文件→`SOURCE_AMBIGUOUS`；换文件后
  `dev/ino` 不符→`CURSOR_MISMATCH`。两者都 fail-closed，不构成权限误发，但**会**复现"永久锁死"症状——
  这与作者自认的 L1b 残留同族，本补丁未解决也未加重。
- **粘贴图片**：`CLAUDE_SKIPPABLE_CONTENT_PARTS` 既有逻辑处理，未受本次改动影响。
- **斜杠命令（新发现，见发现清单 F1）**：真实构造了一条 `origin.kind:'human'`、无 `promptSource`、
  `message.content` 为"展开后文本"（区别于候选排队时的原始 `/xxx` 字节）的斜杠命令行，直接调用被测函数
  实测：抛出的是 `PROVENANCE_MISMATCH`（来自 `validateClaudeUser`，在做字节比对**之前**先做 provenance 校验），
  **不带** `next_native_turn_differs` 标记。在同一构造下对纯净 `dddf8e2` 跑了同一探针，**基线抛出完全相同的
  错误**——证明这是既有缺口、B-L2 未引入也未加重，但也**没有被 B-L2 修复**：若这类人类行被排在队列非末位，
  仍会让整队列硬失败（不可跳过），与本次要修的症状同构。

### C4 · 滥用 — **NOT REFUTED**

cross-session 消息在真实 transcript 里落地为 `type:'attachment'`/`type:'queue-operation'` 行，
`claudeUserKind()` 直接归类 'other'，根本不会被当成"游标后第一条人类行"参与比对；若被塞成**末位**候选，
`final` 恒定重新抛出（跳过判据里 `final ||` 短路），不会被跳过、更不会被认证为 TURN_ACTIVE/SWITCH_ONLY
（冻结测试 "a Claude cross-session message... is skipped once a later turn attests" 已覆盖非末位场景并通过）。

`deactivateProject`（`project-pin.mjs:316`）本身要求 `state ∈ {BOUND, TURN_CLOSED}`，agent 无法在
TURN_ACTIVE 时调用它自我解绑再冒领。deactivate 后重建的 fence 定在**当前**源尾部，任何在 deactivate 之前
排队但未消费的候选全部作废（"deactivate re-fences at the source tail so a turn it discarded cannot
orphan-lock the session" 通过）；要拿到新权限必须有 deactivate **之后**真实发生的人类行，重放已消费事件
仍被 `EVENT_REPLAY` 拒绝（"resetting the ledger on deactivate cannot re-grant a turn consumed before it" 通过）。

**范围说明（非本补丁缺陷，如实记录）**：若 agent 本身就有 Bash 写权限直接向自己的原生 transcript 追加伪造
的 "human" 行，这套机制的信任边界会被突破——但这是整个 attestation 架构的既有信任假设（"transcript 只由
真实 harness 进程写入"），dddf8e2 基线同样成立/同样不设防，不是 B-L2 引入或本应解决的问题，只作范围声明。

## 2. 发现清单

**F1（MAJOR，非本补丁引入，但本补丁未覆盖）** —
`.claude/hooks/lib/event-attestation.mjs:610-613` 注释所称"该候选被拒绝是走
`validateClaudeUser`"是准确的（我最初凭代码注释猜测过顺序，实测纠正了自己的猜测——`validateClaudeUser`
确实先于字节比对执行）：任何 `origin.kind==='human'` 但 `promptSource` 不在
`['typed','queued','suggestion_accepted']` 白名单内的真实人类行（斜杠命令是最常见的具体例子，因为
Claude Code 记录的是"展开后文本"而候选排队时拿到的是原始 `/xxx` 字节，二者天然不等）——若被排在队列**非末位**，
会抛不带 marker 的 `PROVENANCE_MISMATCH`，不满足跳过判据的 `error?.details?.next_native_turn_differs`
条件，导致整队列继续硬失败。**已用直接探针在补丁副本与纯净 dddf8e2 上各跑一次，两者报错完全相同**——
确认是基线既有缺口、未被此补丁修复，也未被此补丁加重，但意味着"本补丁让 harness 合成 prompt 不再卡死
队列"这句话的实际覆盖范围，比字面听起来窄：它覆盖"候选在源里根本找不到对应人类行分类"的情形（task-
notification/cross-session-message 均记录为非 'user' 类型行），不覆盖"候选对应的人类行存在、分类为
human，但 provenance 字段不满足白名单"的情形。建议：要么把 `next_native_turn_differs` 的判定前移到
`validateClaudeUser` 的 provenance 失败分支也可能触发（需要先证明这不会引入新的可跳过窗口），要么在文档/
残留清单里明确记录这是 L1b 家族的一个具体、可复现的子场景。

**F2（MAJOR，测试覆盖缺口，非功能缺陷）** —

函数本身对 Codex 功能正确，但"CLI 全链路（lease/link 快照恢复/CAS 提交点）在 Codex 会话上跑通"这件事，

即可大幅提升信心）。

**F3（MINOR，审计链不足，作者自认软肋，已核实为真）** —
被跳过候选的追责信息只经两条通道：(a) 函数返回值里的 `result.unwitnessed`，(b) 一行匿名、无 session 归属、
