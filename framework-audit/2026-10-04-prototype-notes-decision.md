# 插入节点与能力形式：决策复审

日期：2026-10-04。版本：v5。范围：框架方案设计，尚未实施。此文与主计划、执行手册共同冻结；独立会审结论以 review.md 的同版指纹为准。

## D1. 要决定的两件事

推荐 **一级可调用的薄 `prototype-notes` skill + 唯一共享组件与数据核心 + OD 完成前内部调用**。处理结果仍是用户的那一个原型 HTML。新增的是稳定调用入口，不是另建一个说明产品。

准确插入点为：**UI、交互、可选动效调整完成 → 用户确认当前业务版本 → 说明生成与人工编辑能力组包 → 最终组合验收 → 当前父节点完成**。已有真实确认直接继承；回收成功、测试 PASS、动效完成均不能替代用户确认。

本结论是针对 R-01–14 的最佳适配判断，不声称对所有项目普遍最优。决定权衡的关键不是“框架里任何东西都必须成为 skill”，而是用户有独立发起“给已有 HTML 加说明／更新说明”的真实需求。

## D2. 决策约束与淘汰规则

以下是硬条件。任一不满足，不能用其它优点加权抵消：

| 条件 | 判定情形 |
|---|---|
| H1 同一原型离线交付 | 只拿最终一个 HTML 到空目录也能看原交互、改说明、重新下载 |
| H2 最终设计确认在先 | 确认引用与业务版本吻合；业务版本变化后不继续沿用确认 |
| H3 AI 局部、人工全域 | AI 只覆盖本次新增范围的全部适用交互；人工可操作完整受支持原型 |
| H4 再次调用有明确接单者 | OD 已结束、motion 已结束、用户改过文件后，均能直接进入，不伪造远端回收 |
| H5 一次调用一个完成者 | internal 不写第二份 handoff/state；standalone 不改历史 OD/motion DONE |
| H6 不依赖强制流程图 | 无正式 Brief/未选择 workflow 仍能处理明确输入；真实权限和来源不能省略 |
| H7 每份新字节重新验收 | 新说明、新绑定和组包不可借用旧 final SHA；全原型行为分母保留 |
| H8 可恢复、保留人工成果 | 中断有明确恢复位置；旧快照不能覆盖用户新业务代码或人工说明 |

硬条件满足后比较：是否只有一份逻辑、用户能否找到入口、是否增加无关调用成本、对现有完成合同的修改是否局部。采用可追踪论证，不使用没有权重依据的打分总分。

## D3. 四个候选的最强版本

| 形式 | 最有力的优点 | 关键反例与代价 | 判定 |
|---|---|---|---|
| A 薄公开 skill + 共享核心 + OD internal | 一个入口承接首次与事后调用；数据、UI、保存、合并只有一份；明确双模式完成 | 要增加注册和路由；若 internal 也跑 standalone 完成代码，会重复 DONE；需要本方案 D5 的明确约束 | **选择**，全部硬条件有明确执行合同 |
| B 仅 OD 内置 | 首次 OD 回收上下文完整；用户无需新指令 | 用户把两周前交付、后来手改的 HTML 交回来时，没有未完成 OD 父调用；现有 recover 需要真实远端四元组。若加通用本地更新入口，实质又要承担 A 的职责 | 不选；仅适合永远只处理首次 OD 回收的更窄范围 |
| C 仅共享内部模块，各原型 owner 调用 | 共享实现、各 owner 维持完成权；首次嵌入成本低 | 原 owner 已 DONE 或当前来源不是生成器时，没有可发现的接单者。让每个 owner 各自补重新进入、确认、恢复、合并，会重复协议；加统一公开入口则收敛为 A | 保留其共享核心，舍弃“没有公开入口”这一点 |
| D 全局 HTML 输出 hook | 看似能自动覆盖所有生成工具 | 文件写入不等于最终设计确认，也不能推导新增 scope；临时页、夹具和仅归档文件会被误加工；跨 harness 触发不同 | 不选；只能承担另行授权的机械校验，不能拥有本功能的语义生成 |

对 A 的反证：如果实现把 skill 写成第二套生成器、要求所有输入有 OD receipt、强制走 workflow、或重新复制 runtime，这个实现就违背选型理由，必须 FAIL。公开入口本身不能证明这些问题已解决。

## D4. 为什么是这个节点

| 候选时机 | 优点 | 为什么不作为最终说明生成点 |
|---|---|---|
| Brief 冻结前后 | 事实较完整，易产生文字种子 | 没有最终 DOM 和实际状态；UI/动效迭代会使锚点和说明失效。保留已有事实，不能提前认定交付完成 |
| OD 首次 recover 后 | 有真实 HTML | 设计师可能继续调 UI、交互和动效；“拿到 HTML”不等于 R-10 的“没问题” |
| motion 自动验收 PASS 后 | 动效已有行为证据 | 用户判断尚未成立；没有动效需求的原型也不应被迫先跑 motion |
| **用户确认当前业务版本后、最终父完成前** | 事实、实际结构和设计师判断同时就绪；能统一验收最终字节 | **选择**；说明发现差异时退回原型修订，不能边修业务边沿用确认 |
| 父节点已经 DONE 后自动追加 | 可做单独加工 | 不能静默改掉已交付结果；只允许用户显式发起新的 standalone 调用，生成新的交付记录 |

提前做只读技术检查（资产闭包、现有稳定 ID、兼容性）是允许的；最终文案、锚点注入和组件组包在确认门之后。最终 HTML 中 bootstrap 必须早于业务脚本执行，是**文件内部执行顺序**，不改变设计流程的插入时机。

现有 OD Phase 5 明确“展示后不阻塞提问”。实施须针对 **notes-enabled** 分支加入受限例外：先展示待确认版本，等待或继承真实确认，再进入说明；关闭说明及仅归档维持原路径。不能在 Phase 6 已执行 DONE 后补这个门。

## D5. 调用、完成与恢复责任

| 真实场景 | 接单入口／确认责任 | 完成者与证据 |
|---|---|---|
| OD 尚未完成，含 UI/交互/可选 motion | OD caller 保持当前 Phase；确认后调用 notes internal | notes 返回 exact candidate/accepted ref 和证据，不写独立 handoff/state；OD resolve 最终 notes ref 后完成一次 |
| 用户只要 motion | 仍由 motion 原合同处理 | 不因安装 notes 自动扣住 motion 完成，不自动追加说明 |
| motion 已 standalone DONE，用户再要说明 | prototype-notes standalone，绑定 exact accepted motion 或最新完整用户 HTML | 新 notes 调用写自己的 handoff；历史 motion 不变 |
| 用户直接提供已有完整 HTML | prototype-notes standalone；读取获准实际文件，确认来源、范围和当前业务版本 | 不要求远端 recover、正式 Brief 或历史 OD handoff；新独立验收和交付 |
| 用户仅手改说明后回流 | 同一 standalone 入口，读取最新完整文件 | 静态验证业务快照未变可继承 UI 确认；重新验收说明和最终字节 |
| 用户手改业务代码后回流 | standalone 入口负责 E6 的 rebase；保留原件，采用实际新业务源并重核确认/绑定 | 不能恢复旧快照掩盖修改；分离不可靠时暂停并取得准确业务 HTML |

内部调用只归还结果；由 caller 独立调度 QG、记录真实判决、seal accepted。共享核心不拥有 Human Gate，也不替 caller 写 workflow-state。若用户自行选择包含 notes 的 workflow，才消费该次已绑定节点；本期不改 optional-workflow-graph 使之成为必经步骤。

本地 checkpoint 的子阶段限定为 ITERATING、AWAITING_CONFIRMATION、CONFIRMED_READY、CANDIDATE_REVIEW、ACCEPTED_AWAITING_PARENT；只描述同次调用进度，不新增框架 Completion Status。恢复先核输入与权限，再核确认业务版本、scope/notes revision、候选或 accepted ref；失效部分重做，不重跑 OD 生成，不重复父完成。standalone accepted 后进入自身普通完成出口。

## D6. 最小实现与登记边界

skill 只负责输入、确认门、范围冻结、调用共享能力、返回或完成。共享目录唯一持有内容规范、数据合同、runtime、样式、合并与组包；OD 只写调用约定。具体字段、登记文件和测试在执行手册 E7.4 与主计划 U-009。

注册必须覆盖真实 direct/semantic 路由、两端 alias、输入模式、模型角色、能力声明、目录和生成投影；不能只创建一个 SKILL.md。选择 `core-execution`：生成/执行上下文较大、已有合同指导，关键接受判断仍由独立判官承担；不硬编码账户模型。Codex tier 1 表示可本地执行，不代表已证明浏览器或双端行为。

受保护改动限于 skill-invariants P2 输出模式/P7 的 OD notes 或 motion→notes 完成前例外，以及 handoff 的最终引用消费。不改变 `_NODE`、`_STATUS`、既有写入函数和一次完成原则。其它生成器默认接线延期；它们已产生的明确 HTML 可以从 standalone 入口进入。

## D7. 推翻条件与验收问题

独立会审必须尝试以 B/C 的最强版本推翻 A，并回答：

1. 三条核心调用能否走通：OD 未完成、motion 已 DONE、手改业务 HTML 回流？当前接单者、确认者、完成者是否唯一？
2. 确认绑定的业务版本与完整输入 SHA、notes 修订是否分清？只改说明会不会被误迫重复设计确认？
3. OD 原“展示即止”、P7 保护区、standalone 无图规则是否获得精确而有限的改动？
4. 公开 skill 是否确实消除了 C 的入口责任缺口，还是只多了名字且把决定留给执行 Agent？
5. 是否保留 AI 范围边界、人可全域编辑、旧成果保护和最终字节独立验收？

任一 BLOCKER/MAJOR 未关闭不得定案。若真实 P1 证明同文件隔离/保存或必要 OD 状态不可行，暂停实施并修订受影响技术方案；不得把该未知转换成已通过的工程承诺。当前决策证明的是**在现有约束下最适配的能力入口与生命周期**，运行可行性仍由明确的 P1 执行门验证。
