- 文档用途：指导独立 Agent 制定详细评估执行计划。

## 零、所有后续 Session 必须继承的背景

**luca_gstack 是在 Codex 桌面、Codex CLI、Claude Code CLI 中通用使用的一个框架。评估按三体系及其协同作用组织，最终产出一份统一的评估执行计划。** 本文将用户口述的“Cloud Code”按 Claude Code 理解；该名称不改变通用框架这一评估对象。

用户本次明确要求：“按照它们的通用价值，然后去考虑我的框架上面的这几大模块的问题以及计划的输出。”据此，以下约束适用于目的整理、研究、独立规划、设计、审计、比较、裁决和迁移：

- **以共同用途定义价值。** 从理解任务、组织执行、保持信息连续性和必要的人类控制出发，研究框架在当前模型与实际运行环境能力之上增加了什么价值；这些价值是否值得其规则、协调和维护成本。
- **保持一个框架的规划对象。** 不按三个使用端拆成三套方案、三组模块或平台专项 Session，不预设需要新增适配层、平台分支或配置体系。若证据表明统一目标存在无法消除的能力冲突，记录影响并回到共同用途裁决，不由执行者自行扩大架构。
- **区分能力事实与架构选择。** 模型本身的能力、环境实际提供的执行能力、框架增加的机制，分别作为归因依据。环境名称不充当方案分组依据；必要的能力核实服务于同一方案的可行性判断。
- **通用性不等于采用最弱能力。** 不要求实现方式完全相同，也不凭空假设各处都有同一能力。无法取得必要能力时，先检验现有能力能否以更简单方式达到同一结果；仍不能满足必要控制或用途时明确限制，不静默削弱目标。特有增强的收益不能冒充通用收益。
- **以证据控制复杂度。** 每个保留或新增机制都要说明服务的共同用途、必要能力前提、最小替代及净价值。确需核实环境差异时，只检查可能改变结论的行为与控制点，复用同一任务和判据；不得以此自动扩成全端、全组合的独立评估工程。
- **按模块职责限定范围。** 三体系评估负责通用的任务分流、Agent 协作、Context 提供及其交接；技能内部领域方法、动效或其他具体交付流程仍由技能 owner 负责。技能作为真实任务的消费方或案例时，只检查与三体系有关的输入、输出和控制衔接。发现技能内部问题，记录具体责任边界，不自动扩大为技能重构或新增评估模块。
- **允许高价值交集优先进入。** 主协调者可将直接改善共同用途或评估可信度、且能保留最新提交有效行为的交集列为优先项。先复用现有 owner；确有额外收益才设计最小增补实验，并记录收益依据、责任边界和回归要求。优先项使用既有任务卡，不新增阶段或审批体系，也不扩大实施授权。

本节是共同输入合同，必须随最小任务包和跨 Session 交接传递。执行者不能只读某一阶段而丢失本节约束。

## 一、从最终目的出发

这次工作的最终问题是：

> 在当前模型和实际运行环境能力下，一个通用的 luca_gstack 框架怎样理解任务、组织 Agent、提供 Context，才能更好地完成用户的实际工作，同时保留必要的控制、可靠性与连续性，并使额外复杂度有可证明的价值？

分层路由、Agent 角色、规划门禁、上下文预算等，都是实现目的的手段，全部可以成为被评估对象。

需要验证四组双向假设：

| 问题 | 两种都必须允许成立的结论 |
|---|---|
| 旧规则是否仍必要 | 仍能防止实际失败；或者可以精简、交给模型或原生能力 |
| 多 Agent 是否有净收益 | 分工提高质量；或者协调、交接和验证成本抵消收益 |
| Context 协议是否有效 | 提供必要信息；或者造成缺失、干扰、冲突和恢复失真 |
| 问题究竟来自哪里 | 架构原则不适合当前能力；或者只是局部实现、配置或接线错误 |

评估覆盖三个体系及其交互，不预设“减少规则”“增加自主性”或“重写框架”就是成功。

**判断依据同时包含：真实工作中的收益、未见任务的适应能力、低频但高损失的失败。**

### 分 Session 的整体安排

主 Session 是协调与集成角色，不承担持续阅读全部代码、研究原文和执行日志的职责。它最初阅读总计划，确定当前获准阶段；随后持有共同输入合同、目的契约、阶段状态、依赖关系和待裁决事项。Session 按目的、研究、模块和验证职责分工，环境差异作为相关任务中的局部取证项处理。

**当前要解决的是“如何分 Session 制定详细评估计划”，不是立即分 Session 开始评估。** 各 Session 名称表示未来的逻辑分工，本轮不创建或启动这些执行会话。

| Session／上下文 | 工作范围 | 必要输入 | 返回主 Session 的内容 |
|---|---|---|---|
| 主 Session | 统一目的与共同比较条件、分派任务、集成计划 | 本总计划；之后按需接收 P0—P1 的中性摘要 | 阶段状态、冲突裁决、统一执行计划 |
| 目的与基线 Session | P0：U-001、U-002 | 用户原始诉求、获准读取的历史与现状资料 | 目的契约、事实基线摘要、证据索引、需用户决定的事项 |
| 研究 Session | P1：U-003 | 目的契约、能力问题和定向研究范围 | 能力证据摘要、实验可行性、来源索引 |
| 路由规划 Session | P2：U-004 的路由分项 | 共同任务包、路由评估问题和中性能力资料 | 路由局部评估计划、需要其他模块提供的条件 |
| Agent 编排规划 Session | P2：U-004 的编排分项 | 共同任务包、编排评估问题和中性能力资料 | 编排局部评估计划、跨模块依赖 |
| Context 规划 Session | P2：U-004 的 Context 分项 | 共同任务包、Context 评估问题和中性能力资料 | Context 局部评估计划、输入与交接要求 |
| 独立方法审查 Session | P2 的终版验收 | 用户需求、冻结的统一计划与验收标准 | 逐项判定、证据、未解决的关键缺陷 |

**例子：**主 Session 先给三个规划 Session 同一份目标与比较条件，各自只展开本模块。三份局部计划返回后，主 Session 统一同一条端到端实验的任务、输入和结果判据，合并重复实验，解决模块间的依赖，再提交一份执行计划。用户不需要在三个窗口之间转贴完整聊天历史。

在运行时支持时，可用三个独立上下文的子 Agent 实现这三项分工，用户只跟随主 Session；不必为每个模块创建可见的新聊天。若用户选择独立可见聊天，主 Session 按产物路径回收交接；跨聊天消息只在已获用户授权时发送。

### 每个 Session 的输入与交接

每次分派只包含以下最小任务包；总计划作为可定位的参考源，执行者不必每次从头读全文：

1. 本计划“零、所有后续 Session 必须继承的背景”、用户已确认的共同目标、必要边界和当前获准范围；本节较短，直接放入任务包，不依赖执行者自行发现链接。
2. 本 Session 的 U-ID、待回答问题及本计划对应章节。
3. 明确的输入材料清单、信息禁区和固定输出路径。
4. 所依赖的上游结论与证据索引，不附上游完整聊天或全部日志。
5. 完成判据、预算、停止条件及需要回传的跨模块问题。

交接采用同一份 Markdown 产物，包含以下五部分：

1. **当前获准范围：**阶段、U-ID、允许的动作／文件范围，以及可核对的用户授权引用；区分获准规划、获准评估和获准实施。
2. **当前结论与证据：**已完成的计划／工作、验证结果和原始证据索引。
3. **依赖与未决事项：**尚未完成的任务、关键决定、在途 Agent 及其责任；附共同输入合同及会影响后续结论的能力前提，防止交接后改按平台分工。
4. **有效产物版本：**统一计划及相关局部产物的固定路径、版本或摘要；待审草稿与获准计划分别标识。
5. **准确恢复入口：**下一 U-ID、按序读取清单、恢复前需核对的范围／版本及阶段门。

摘要用于导航，完整局部计划用于集成；主 Session 不能仅依据摘要就宣称整份计划通过。原始证据保留在执行 Session 的产物中，需要核查时才定向读取。

若一个模块读物或实验本身过大，按问题或实验批次继续拆分；交接后用新上下文承接。若主 Session 也已积累过多材料，则将上述五部分保存为集成检查点，用新的主 Session 恢复同一协调角色，不重新导入全部历史。

新主 Session 先按恢复入口核对现行计划版本、原授权及其范围，再恢复下一任务；“已完成／待执行”状态本身不是授权。原授权仍有效且范围未变时，不重复请求批准；引用缺失或无法验证时停在规划，不能自行进入评估或实施。

详细计划必须确定输入包与返回摘要的容量上限、原始日志的存放方式和检查点时机。可用时依据运行时上下文指标判断，无法测量时保守控制读物和任务批次；不能把固定聊天轮数宣称为实际 Token 占用率。到预算边界仍未完成时返回未完成事项，不截掉关键依据后冒称完成。

## 二、先把真正的评估执行计划做扎实

保留原任务编号。本总计划获准后，先执行 P0—P2；其产物通过审阅后，才进入正式评估。

### P0：建立目的契约与事实基线

#### U-001：还原并确认目的

由目标整理者将材料分成三类：

- 用户希望获得的结果。
- 用户今天仍认可的必要边界与不可接受损失。
- 当年成立、今天需要重新验证的假设。

历史材料可以解释原始目的，但不能直接把旧模块、阈值和流程升级为新设计要求。另一名独立审查者检查目标包：去掉旧实现名称后，是否仍能清楚描述成功。

将本计划第零节作为用户已明确的目标约束继承，无须重新询问是否要通用框架。把“我要获得的共同结果”与“目前恰好使用的工具、模型和入口”分开；有价值的能力增强可以评估，但不能把某一端的功能偏好转写成全部用户任务的必需流程。

涉及真实偏好的问题，如质量与速度如何取舍，由用户集中确认；能够查证的事实由 Agent 自行调查。

#### U-002：确认当前实际基线与任务分布

记录当前版本、未提交变化、执行环境，以及“文档宣称的能力、权限允许的能力、实际可调用的能力”之间的区别。不能把当前系统直接当成半年前的系统。

本轮提交核对基准为主仓 `05120197073144c0f46b6fb30a192733d529cc4f`（2026-10-02）。正式 P0 仍须核对当时 HEAD 与相关未提交内容；有新变化时只更新受影响的事实、方法引用和任务，不回退或重做已经合并的模块改进。

最新提交保护范围包括已生效的技能用途、必要控制、输入输出与交付契约，P0 按实际来源列入回归基线。候选试验在获准的隔离范围内进行，不覆盖主仓、回退提交或直接改动受保护模块。保护有效行为与契约不等于冻结每条实现细节；需要改动的提议仍须证明兼容，不能用新方案收益抵消未经用户接受的回归。

围绕共同用途记录最小必要能力及证据来源，例如能否独立分工、保留必要信息、恢复任务或执行控制。只在差异可能改变方案可行性或结论适用范围时，补充具体环境、版本和可用性证据；不预先生成三套系统画像。模型能力、环境能力和框架规则混淆时，标为待区分的解释，不把“模型能理解某协议”当成“环境已执行该协议”。

将用户认可的必要边界与待评估的框架规则分别记录；评估宿主可以遵守当前真实权限，但不能未经论证就把旧框架规则当成候选设计必须继承的目的。证据读取范围列入任务包，不因需要样本而自动扩读所有项目。

根据近期实际任务和用户的使用描述，区分产品工作、框架维护、简单任务、长任务等。资料不足时标注未知，不能凭印象设置评估分母。

**交付与验收：**形成中性目的契约、事实基线和任务分布说明；每项必要约束有来源，关键价值取舍已经明确。

**必要性：**缺少这一步，后续可能非常严谨地优化一个用户并不真正需要的目标。

### P1：确定值得调查的问题及可行的取证方法

#### U-003：先开放发现，再定向深挖

先对现代原生 Agent 能力、编排方式、Context 方法及其失败证据进行有界扫描，允许发现尚未想到的问题。

随后围绕会改变判断的争议，深入查阅官方文档、源码和论文。每个研究分支必须说明：

> 它可能改变什么决定？目前缺什么证据？何时可以停止？

不固定必须研究几家框架，也不把知名框架的做法直接视为本地答案。本阶段研究到足以制定可行实验；完整的深度调查安排在正式评估执行计划中。

研究按共同决策问题组织，提取机制、成立条件和失败证据。对于来自模型 API、自建 Agent 框架或现成执行环境的结论，注明能否迁移到本任务；不得直接把 API 级能力等同于用户实际工具中可用的能力，也不按品牌分别编写方案。框架与原生能力的重复、互补或干扰均作为待验证假设。

**交付与验收：**问题—假设—证据需求表、可比机制清单、实验可行性与限制。每个主要问题都有能区分竞争解释的取证办法。

**必要性：**既避免沿用旧能力假设，也避免先读大量资料、最后仍不知道该验证什么。

### P2：让独立 Agent 编制真正的执行计划

#### U-004：将目的和方法编译成执行合同

冷启动的计划 Agent 只接收中性目的、当前能力证据、任务条件和本总计划；不接收旧机制及旧审计结论。

U-004 由三个模块规划 Session 提供输入、主 Session 集成、独立审查 Session 验收。拆分使用 U-004-a（路由）、U-004-b（编排）、U-004-c（Context）；原 U-004 继续表示统一执行计划，不重编其他任务编号。三者产出的是评估子计划，不是提前替代 P3 的独立体系设计。

三个模块须围绕以下共同问题编排取证，不再按使用端二次拆分：

| 分项 | 核心决策问题 | 与其他模块共同验证的影响 |
|---|---|---|
| U-004-a：路由 | 哪些任务确实需要显式分流、升级或人工决定？现有层级是否改善选择，还是造成误分、截流或重复判断？ | 路由引发的拆分、等待及信息要求是否值得 |
| U-004-b：编排 | 何时单 Agent 已足够，何时独立分工、并行或审查有净收益？角色、依赖和控制如何保持必要且简单？ | 分工收益是否被重复规划、协调和交接损失抵消 |
| U-004-c：Context | 什么信息应在何时、以何种粒度提供，才能支持正确行动与恢复？筛选、压缩和交接是否丢失依据或放大干扰？ | Context 是否承接路由意图、编排责任和必要控制 |

它必须比较完整评估与两个更小的方法——只做静态审计、直接做局部实验——说明哪些问题需要独立设计和行为比较，哪些可以用更便宜的证据解决。

最终计划必须明确每项任务的：

| 必填内容 | 要解决的问题 |
|---|---|
| 决策问题、需求来源 | 为什么要做 |
| 共同用途、必要能力前提、结论适用范围 | 通用价值是什么，哪些事实需要核实 |
| 输入白名单、信息禁区 | 可以依据什么，如何保持独立 |
| 负责人、独立验收者 | 谁产出，谁判断 |
| 动作、产物、证据标准 | 具体做什么，怎样算完成 |
| 依赖与解锁条件 | 何时能够开始 |
| 时间或调用预算 | 做到什么程度 |
| 继续、停止和失败出口 | 何时扩展，何时结束 |

每一步还要回答：**删掉这一步，会让哪项决定失去什么证据？**回答不出来，就删除、合并或改为条件步骤。

样本数量、重复次数、收益门槛和实验上限，应依据 P0—P1 确定，并在实验前冻结。价值取舍由用户决定，技术参数由计划 Agent 提出并接受方法审查，不能留给执行 Agent 临场随意选择。

#### 主 Session 的集成责任

合并必须作出整体设计决定，不能只是拼接三份 Markdown：

- **统一实验接口：**对同一任务使用共同的原始输入、可观察结果和证据格式；各模块以这些结果评价，不以旧模块名称定义正确性。
- **检查交互：**明确谁作路由决定、谁组织执行、谁提供 Context，以及三者交接处的冲突、信息丢失和重复门禁如何被测到。
- **排序依赖：**单模块研究可并行；跨模块条件未解决时，不让执行者自行补全不同的假设。
- **去重并核算整体预算：**共享端到端实验复用，整条任务链累计资源；三个局部计划各自有预算仍不代表整体成本合理。
- **审查通用性和复杂度：**共同目标、规则含义和模块交接保持一致；排除没有证据必要性的按端分支。环境能力冲突只回到受影响的任务，不扩成三套规划。每项新增机制均要与更薄替代比较维护成本。
- **形成一份执行真值：**局部计划保留来源与版本；后续执行以经过审查、获准的统一计划为依据。

详细执行计划至少交付：继承共同输入合同的目的与证据索引、统一实验／任务卡与 Session 分配表、整体预算和停止规则、逐项验收及恢复读取清单。环境能力前提、已证实范围和未验证限制附在相关任务中，不另造平台计划。关键价值取舍未决时不能提交为可执行定稿；局部技术问题交回对应规划 Session 修订，不要求三者全部重做。

#### 复用现行方法，避免模块重叠

本次评估的调度、交接与验收沿用现行 Plan／Orchestrator／Quality Gate 合同；不新增平行调度器、任务状态机或通用验证协议。以下三处交集直接关系到比较证据的真实性，列为本次优先复用项；详细字段留在唯一 owner 中，不复制到本计划：

- **多来源或多 Session 证据汇总：**首次派发多个来源切片或测量分支前，完整读取 `.claude/agents/references/evidence-receipts.md`。主协调者预先冻结应读范围、版本、方法及依赖断言；返回实际工具证据与缺口，汇总时保留全部原分母、失败及拒绝理由。摘要、文件 hash 或自报 EOF 均不能代替真实读取证据。
- **当前对象的行为验证：**冻结首个 required 行为 TEST 前，完整读取 `.claude/agents/references/project-verification.md`。优先复用足够的现有 suite，只补最小缺口；绑定当前版本、实例／会话、数据、driver 与完整断言，保留失败和清理后的证据。就绪检查不能替代功能 TEST。
- **断言与失败出口：**直接遵循 `.claude/agents/plan-agent.md`“块 3”的退出码契约，按 BLOCKING／WARNING 决定依赖能否继续；不得由输出 PASS/FAIL 文本或末尾成功命令掩盖真实失败。

上述规则约束评估工作怎样取得可信证据，不要求独立候选架构复制当前实现。技能特有的原型、动效或交付协议只在真实案例触发时由对应 owner 承接，不升格为三体系的普遍前置步骤。当前提交的具体机制和重叠核对记录留在主协调／现状侧；独立规划与设计侧只接收共同目的、中性事实和必要的方法合同，不接收现状审计判断。

**交付与验收：**一份可直接委派执行的详细计划，并通过独立审查。它必须完整展开下面的 P3—P6。

## 三、真正执行计划必须包含的验证链路

### P3：独立设计与现状审计

- **U-005 独立设计者**接收目的、能力证据和开发案例，从目标推导候选方案及其失败预测。
- **U-006 现状审计者**接收旧实现、历史资料和运行证据，重建实际行为及有效用途。
- 双方冻结前不接触彼此结论；冻结后由第三方首次汇合对照。

双方都继承第零节和同一目的契约。设计者从共同用途推导机制，不预设“统一核心＋多个适配层”等架构答案；审计者辨别共同价值、历史补偿和重复控制，环境证据只用于解释实际行为。共享事实包由目的与基线阶段形成并审查，不能由审计侧临时将旧规则包装成能力前提传给设计侧。

现状审计必须覆盖完整用途：

**用途 → 入口与触发 → 行为 → Context 需求 → 人工控制 → 故障恢复 → 证据。**

独立性通过输入清单、工具访问记录、版本和解盲记录验收。`fork_turns=none` 只证明没有继承会话历史，不能冒充物理隔离。若自动注入旧设计约束或访问禁区，重做受污染部分；环境持续无法满足隔离时，应报告限制，不能反复重启后自行宣称合格。

正式评估继续沿用独立上下文：目标导向设计、现状审计、冻结后对照各有自己的 Session。现状审计可按三个体系拆分，但审计材料只在审计侧汇集，冻结前不得通过主 Session 的共享摘要流入独立设计侧。

输入独立与运行独立分别验收。候选运行时若仍被旧 hooks、路由或 Context 注入改写，就不能把结果全部归因于候选；详细计划必须规定测试环境及允许的宿主机制。无法隔离时限制结论，不为取得新方案成绩而修改生产环境。

### P4：公平比较并解释差异

**U-007 建立比较矩阵，U-008 执行行为验证。**

至少考虑三个方向：当前体系、针对性精简、目标导向的独立候选。被硬约束、可行性或等价证据排除的候选，无须继续制作原型。

此外必须考虑“当前宿主原生能力＋完成任务所需的最薄提示与资料”作为对照，以回答自建框架是否仍提供额外价值。它可以与某个候选合并；无法公平纳入时说明排除依据和结论限制，不为凑数量制作第四套系统。

比较的主轴是同一任务上框架机制的增量价值。对照各方在同一实际运行条件内比较；不同模型或环境下的绝对成绩不能直接当成框架优劣的因果证据。环境取样依据共同用途与关键能力风险决定，不按三个端机械复制整套实验。涉及跨环境成立的关键结论时，使用同一行为判据核实其必要前提；证据不足就限定适用范围，不以单处成功宣称全面通用，也不以缺证据自动增加平台架构。

进入实证比较的候选必须能够处理相同任务，产生可检查的结果。详细计划须明确薄原型的实现者、范围和预算；未实现的能力只能作为设计推断。

比较遵守以下条件：

- 主实验固定当前模型、运行参数、可用工具、权限、原始资料与预算条件。
- Context 的检索、筛选、压缩和组织方式是被评变量，不能强行固定最终注入内容。
- 多模型调度若属于待评机制，单独设计实验，避免与架构差异混为一谈。
- 旧模型只有在实际可用、且比较可能改变结论时才纳入；不能用历史成绩冒充同期对照。
- 开发集与隐藏验证集分离，保留验证集首次结果。看过并用于调优的案例不再算未见验证；验证材料用尽也是停止条件。
- 冻结对象包括实际实现、提示词、配置、资料和环境，确保结果对应完整版本。

按完整任务链累计主 Agent、子 Agent、重试和候选自身验证的成本；独立研究与评分开销另列。比较同一总资源上限下的质量，以及达到相近质量所需的资源与用户等待时间；一次性建设／迁移成本与每次运行成本分开。实验批次可使用新 Session，但重置状态和输入条件必须对各候选一致。

先验证完整链路：

**意图 → 路由 → Agent 编排 → Context 交接 → 行动结果。**

再对有争议的机制进行单独或组合消融，解释收益和损失来自哪里；不默认穷举全部组合。

### P5：反证与裁决

**U-009 发起独立挑战，U-010 裁决并复验。**

详细计划必须事先规定方案优选方法：

1. 先通过用户确认的必要控制和关键用途底线。
2. 再依据预先确认的质量、可靠性及效率取舍比较。
3. 将规则与配置数量、用户需要作出的额外选择、协调交接负担、维护与迁移成本、新增失败风险计入净价值；不能仅用 Token 变少或文件变短证明简化成功。
4. 对“更准但更慢”等冲突，预先规定选择规则或需要用户裁决的条件。

不能看到结果后再改变权重，也不能仅凭综合印象打出一个总分。

独立挑战须检查两种相反错误：为追求通用而削弱必要能力，以及为局部能力差异引入不必要分支。若共同用途与实际能力确有冲突，裁决记录缺口、可行的最小替代和影响；涉及降低用户已确认的必要边界时交用户决定，不能自行选择牺牲一端或维护多套体系。

计划方法审查和最终结论反证各有不同对象，均须进行。领域专家只用于重要争议；默认最多两轮，并非必须跑满两轮。修复关键缺陷后复验终版，合理分歧保留。

### P6：价值结论与平滑迁移

**U-011 给出净价值判断，U-012 给出迁移方案。**

每项既有有效用途必须落到以下一种处置：

- 新体系有可验证的新路径。
- 暂时保留旧路径。
- 经用户接受后退出。

不要求每一条旧规则原样存活，但不能静默丢掉用途、控制能力和恢复能力。

兼容以用户结果、必要控制、下游可消费的接口／状态和恢复要求判定，旧步骤只作为证据。每项用途写清允许变化，避免把逐规则继承误认为平滑迁移。

迁移围绕同一套共同用途、规则含义和交接合同组织；必要的入口或执行差异记录在相关用途的验证证据中。最终结论逐项说明保留、精简、替换或退出的机制及其净价值、能力前提和验证范围，形成一份统一建议，不交付三套互相独立的平台路线图。

迁移方案包含旁路对比、按风险分批切换、回退触发条件、状态恢复和旧路径退出标准。评估阶段验证这些安排的可行性；生产切换另行形成实施授权。

## 四、怎样防止遗漏、过度和“审到好评”

以下七项是总计划与下游详细计划的验收标准：

1. **目标忠实：**每个主要目标可追溯到用户的诉求，明确评估一个跨环境通用框架的三体系及其交互；旧做法没有未经论证变成硬要求。
2. **步骤必要：**每一步支持明确决定，并说明删除损失；昂贵步骤有扩展条件，没有按端复制计划、未经证明的适配复杂度或与技能 owner 重复建设的机制。
3. **比较公平：**对象可测，任务与条件可比，优选规则事前确定；模型、环境与框架影响可区分，结论适用范围有证据。
4. **独立有效：**输入、访问、冻结、解盲和污染处置均可核查。
5. **指导可执行：**任务有明确输入、动作、产物、责任、验收及失败出口；各 Session 接到共同输入合同，能力冲突有明确处理方式。
6. **研究有终点：**局部与整体预算、停止条件和证据不足出口明确，不以所有人赞成为结束条件。
7. **结论可落地：**形成统一建议，覆盖三体系交互、有效用途延续和迁移代价，清楚区分实测与推断；通用性没有被偷换为最弱能力交集或无证据的全端可用。

关键缺陷未解决，就修订相关部分；不降低标准换取通过。若充分比较后无法证明改变值得，保留现状就是有效结论。

最终推荐的含义是：**在明确的目标、任务、能力和资源条件下，经过可行替代方案比较与反证，证据最充分的选择。**

Session 拆分另外检查三件事：每个输入包可单独理解自己的任务；交接没有丢掉关键证据或把禁区材料传给隔离角色；统一计划中的跨模块决定已经明确，不留给执行 Session 临场拼接。拆分本身不是收益证明；需要实际记录各 Session 的输入量和交接负担。
