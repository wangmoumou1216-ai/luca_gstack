## 结论

辅助会话指出的两个阻断成立，但“缺收据 + 不允许脚本”还只是局部原因。

更准确的问题定义是：**框架接收了“交互原型植入已有模板并重新设计”的合法任务，却没有为它提供完整可执行的路径：计划准入依赖尚未实现的批准来源证明，模板执行只覆盖受限静态编辑和独立视觉精修，流程又没有在承诺交付前明确核对这些能力。**

这里同时存在入口路由缺陷、批准机制缺口、模板能力缺口和验证缺口。不能用其中一处修复代表整条流程修复。

## 三类问题的边界

| 问题 | 已确认事实 | 归属及影响 |
|---|---|---|
| 未沿设计流程找模板 | 原请求明确要求走设计流程，Agent 最初直接索要路径；后经纠正才发现正确模板 | 路由及跨轮任务承接；另一会话正在修 |
| 计划无法进入执行 | Plan owner 明文要求 native approval receipt，又明文说当前没有该能力 | 共享框架合同与执行准入缺口；不是当前项目选择 hook 报错 |
| 交互原型无法植入 | 实际菜单函数只更新选中项、标题和 aria-label；适配器拒绝新增脚本/事件 | 共享模板适配能力缺口；不是模型不会写 JavaScript |

此前“子代理来源不受信任”的 hook 故障在原任务后续已有成功回报，不能再作为当前阻断的原因。
使用相同规则和同一原件适配路径时，Luca app 与 Codex app 都会受到后两项限制；是否在某次任务触发，取决于任务和路径。此判断不等于两端完整流程已实测。

## 批准问题：字段一致性与真人批准来源之间缺少连接

`.claude/agents/plan-agent.md:423` 要求首次派发/effect 前做批准、身份与依赖图检查；426–427 行又禁止在缺少可信 native approval primitive 时接入首次派发。593 行后的批准门要求真实、范围匹配的确认。

`scripts/check-plan-approval.mjs` 能核对路径、计划 SHA、scope、effects、时间格式和 `confirmed_by == user`。但最后一项只是字符串比较，工具没有消费真人消息、会话来源或可信回执。它的 PASS 是票据字段一致，不是批准来源真实性的证明。

本轮运行 `node scripts/test-plan-approval.mjs`，退出 0。该测试自行生成 JSON 后 PASS，证明的是上述一致性检查；它并未证明“真人确认 → 可执行计划”链路成功。没有使用这些测试票据执行任何真实效果。

这不意味着框架完全没有原生事件基础设施。`.claude/hooks/lib/event-attestation.mjs` 已有真实用户事件的溯源接口，Luca 的受保护来源 scope 也有独立处理。**缺的是将经核验的批准消息绑定到具体计划和执行范围的接线及验证。** 不能直接把项目身份、事件真实性或工具命令许可当成计划批准。

另一会话也遇到了同一缺口，最后取得用户对“本次对话确认替代收据”的具名例外。该例外只适用于它的具体计划；没有补齐框架通用批准机制，也不授权其他任务照搬。

## 模板问题：任务要求与执行能力不匹配

`design-brief/SKILL.md:57` 接受已有原型加模板的入口；输入合同同时要求继承行为、分别处理植入与精修。

实际执行只有两种原件路径：

- `original-preserving-v1`：局部静态增删改；原有脚本和样式保持，新增脚本/事件拒绝。
- `original-ui-refinement-v1`：原节点内 class/style 的有效变化；不能改变业务 DOM、行为属性或脚本，不能混入 add/modify。

原模板 `crm-workbench-home.html:808` 的 `selectMenu` 没有工作区内容切换。新增六个菜单与六个业务工作区联动需要补充执行逻辑，仅插入静态内容不能实现完整要求。

本轮使用主检出的同 SHA 编辑器，针对真实模板 `workspaceCard` 执行内存中的局部输出校验；浏览器隔离上下文屏蔽网络，原模板脚本未执行，未落盘或交付修改后的页面：

| 探针 | 实际结果 |
|---|---|
| 在内容区追加静态 section/button | PASS；语义验收仍 PENDING |
| 相同位置追加工作区脚本 | `ACTIVE_CONTENT_FORBIDDEN` |
| 相同位置追加 onclick 行为 | `ACTIVE_CONTENT_FORBIDDEN` |
| 同一动作集包含结构插入和视觉 refine | `ORIGINAL_REFINEMENT_PROFILE` |

这些结果复现了适配器能力边界，不是完整产品端到端复现。

还存在组合上的缺口：`prepareOriginalCopyHandoff` 从登记的 source-manifest 固定读取原件（`scripts/original-copy-handoff.mjs:34`），没有直接接受经验证的上一步衍生产物作为新基线。因此“分两步，先植入再精修”目前不能只靠一句流程指令保证成立。

保护原件、保护未授权区域的目标合理；但将“保留原有行为”实现成“当前路径没有新增行为能力”，无法满足本次已授权的业务接入。

## 推荐方案

### A. 接通真实批准到计划执行

保留真实用户批准和精确范围检查，补现有检查器与原生消息来源的连接：

1. 展示可审阅的计划及允许效果，绑定计划身份和版本。
2. 从当前宿主可核验的真实用户回复取得批准依据；计划展示与回复之间必须有明确绑定，含混回复不能自动扩权。
3. 由受信任的运行时边界生成/核验记录；模型填写的 JSON 只作索引，不能生成权限。
4. 执行端核验同一批准来源、计划版本、项目/仓库、效果范围及撤回/失效条件；漂移或换范围只重批受影响部分。

优先复用已有事件溯源和宿主适配，不新造完整权限引擎，也不假设两个 app 共用同一来源目录。真实批准如何取得与证明须分别验证。若某宿主暂缺能力，提前声明该执行分支不可用。

不推荐永久依赖“本次例外”，也不推荐把任意 `confirmed_by: user` 当真人签字。

### B. 为交互原型接入提供有限、可审查的模板扩展路径

保留既有静态和视觉精修路径；新增能力只服务明确要求业务植入的任务。第一版以本次六菜单案例为最小纵向验证：

- 不可变原件继续作为基线；所有变化发生在项目副本。
- 一份适配契约分别声明结构改动、行为接入、视觉改动和保留范围，全部来自同一需求来源。
- 明确六菜单的稳定映射、内容挂载点、允许新增的控制逻辑、必要的原菜单连接点、样式范围和资源闭包。
- 对范围内代码变更做独立审查，对范围外字节继续严格校验；只允许“已审查的具体新增逻辑”，不开放任意脚本字段。
- 本次结构、行为和视觉改造可以在同一个受控衍生产物中分别验证，避免未经实现的“衍生文件再当原件”假设。只有确需多轮适配时，再补充明确的父子版本来源链；不把每次产物重新登记成模板库资产。
- 新脚本与原脚本处于同一页面时，DOM 范围声明本身不是安全沙箱；必须依靠实际代码审查和行为回归，不把声明/哈希包装成执行隔离保证。

这一能力需要同步 page-context、原件编辑/交接实现及 Brief/OD 的能力消费规则。仅在提示词中写“另审精确范围”没有可执行出口。

### C. 把能力判断提前，阻断只作用于依赖它的动作

用户确认模板后，先给出三个独立结论：语义适合、动作/状态适合、当前执行路径可用。能力未知不得包装成“准备好了”。

源内容盘点、需求继承、语义映射和契约草稿可以在其实际授权范围内推进；完整冻结、执行承诺与外部生成必须等待关键能力冲突解决。输入合同已经允许“仅 connector 不支持时保存契约、执行 BLOCKED”，应在计划中真正贯彻。

批准机制缺失也不应阻止无需该执行批准的只读诊断。与此同时，不可用“仍在准备”扩大项目写入、代理派发或外部效果权限。

原件路径另有 HEADLESS_ONLY、显式 opt-in、具体目标和 stage/run/recover 授权等条件。这些是后续必须核对的条件，不能宣称修好脚本限制后整条链就必然成功；尚未发生的缺口也不应提前记成已复现故障。

### D. 用本次事故验证整条路径

复用真实请求及短回复序列，在有明确范围的隔离实例中验证：进入设计流程 → 自行找到模板 → 继承模板确认 → 展示具体计划 → 真人批准确实被执行端接受 → 六菜单及原型关键交互可运行 → UI 改造和保持区通过验收。

回归必须同时包含：伪造批准、旧计划批准、错误项目、撤回后执行、未批准脚本和越界修改被拒绝；有效批准与已审查的业务接入能够成功。只有拒绝测试通过，不能证明流程可用。

Luca app / Codex app 分别验宿主来源；Claude / Codex 分别验 harness 消费。两组维度不同，不以一个端的成功覆盖另一端。

## 实施边界与取舍

建议先完成 A 的最小批准闭环和 B 的单案例适配验证，再扩大覆盖；C 应随这两个 owner 的变化落地，D 为共同验收条件。复用另一会话的路由改动，不增加一套 workflow 引擎。

当前不建议增加流程关键词、重复模板检索能力、关闭现有保护、默认改成 reference_only 或替用户切换设计工具。这些做法都不能完成已经确认的“真实模板 + 交互接入 + 重新设计”。

方案仍需在实施时冻结准确改动范围和测试实例。本轮没有实现批准桥、交互扩展或执行 OD，也没有取得这些能力的端到端成功证据；因此结论是问题定位与方案明确，框架修复尚未实施。
